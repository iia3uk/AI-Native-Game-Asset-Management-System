# Architecture

`server.mjs` is the loopback HTTP adapter. The browser renderer lives in `public/`, with the 3D stage separated from catalog UI and thumbnail scheduling. Legacy local grouping and Unity material resolution are currently in `scripts/`. Fab remains a separate file-backed source.

`core/files/` owns scoped file access, discovery and the shared format registry. `core/index/` owns SQLite, migrations, assets, version history, full-text search and review fields. `core/analysis/` contains technical analysis and quality profiles. `core/processing/` owns the durable queue, worker lifecycle and library watching. `core/thumbnails/` contains the PNG renderer and its cache. `core/http/` adapts the core APIs for the browser. Indexed search results open in the existing renderer.

Asset roots are user-selected, canonical directories. Discovery skips child symlinks and junctions. File paths stay relative to their root until opened. Application paths are resolved by `core/config/data-paths.mjs`.

The SQLite job queue records scan progress and permits one active scan job per library. The HTTP process claims jobs using a renewable lease. The successful result and updated assets commit in the same transaction. Pending jobs resume after startup. An expired running job is marked interrupted and can be retried.

`LibraryWatcher` registers native recursive notifications for roots with an explicit SQLite opt-in. It groups nearby events into incremental scan jobs and retains changes received during a running scan for a follow-up. It reconciles at startup, when an unavailable root returns, and every 15 minutes. Reconciliation also covers filesystems without usable native notifications. Automatic jobs run at a lower queue priority than manual jobs and share the same discovery and path checks.

The scan reads bounded glTF/GLB/VRM and Wavefront OBJ/MTL data and supported image headers outside the SQLite transaction. It reuses existing analysis when the processor version, path and content still match. Technical metrics and explicit dependency rows commit with the asset updates and scan result. Dependencies resolve within the same library's committed index. OBJ texture links resolve one step through indexed material libraries, so changing a texture or MTL updates the next report without rewriting the OBJ.

Quality validation uses the current index report and the selected profile on demand. Profile edits use optimistic revisions and store their overrides in the same SQLite database, including backups. Evaluation is shared across interfaces and requires no extra scan.

Thumbnail generation uses the SQLite jobs table and a dedicated worker slot, so scans and previews can run concurrently. A lease and a unique index cap rendering at one running thumbnail job per database across the HTTP server and CLI. Pending work survives restarts. The renderer uses the pinned Three.js geometry loaders and a bounded software rasterizer in a terminable Node worker. The source and indexed geometry buffers must match their recorded file fingerprints and SHA-256 hashes. Publication checks the lease and source version and atomically renames the PNG from a staging file.

Generated 160 × 160 PNGs live in an application-owned directory shared by the HTTP server and CLI. The key includes content hashes, relative geometry buffer references, processor version, format and resolution. Thumbnail retrieval verifies current indexed inputs before serving output. A 64 MiB default quota evicts the least recently used files, and entries expire after 30 days without an HTTP image read. The cache is disposable and separate from database backups.

`core/packages/archive/` handles bounded archive reads. `core/packages/unity/` separates package limits, path validation, inspection, report generation and staged publication. The Unity importer uses the same SQLite queue as scans and thumbnails. One import can run per database at a time, with at most 16 active or queued imports. The browser UI lives in `public/package-importer/`.

Inspection streams TAR.GZ content and fingerprints the compressed bytes. Import checks that fingerprint before publishing to `imports/unitypackage-v1/<sha256>` under the data directory. The original Unity tree is kept in `Source/`, with package PNG previews beside it in `Previews/`. Library registration, follow-up scan creation and completion of the import job share one SQLite transaction. A crash after directory publication can leave a reusable completed export on disk. A retry verifies the archive SHA-256 and reuses the output.

`core/engines/` combines Unity, Unreal and Blender discovery adapters. Each reads a bounded set of local directories and installation metadata. Unity matches `ProjectSettings/ProjectVersion.txt` against Hub versions and can identify a candidate from the same series. Unreal matches `EngineAssociation` against known versions or registered build IDs. Discovery reads installation and project metadata without launching the editors. The existing Blender preview calls the Blender discovery adapter when its explicit executable setting is absent.

Schema 8 stores optional export formats on the import job. `core/conversion/` manages model format selection, artifact verification, categorized publication and reuse. Exports are staged under `imports/unitypackage-v1-export-v1/` and keyed by source SHA-256, requested formats, conversion version and the discovered Blender executable identity. Verified originals and generated artifacts are indexed under the same export root. Extraction-only jobs continue to index `Source/` for the existing layouts. The report records the method and SHA-256 for every published artifact and the Blender version when used.

Schema 9 adds the mode and requested Unity version to the job and to the cache recipe. `core/engines/unity/bridge/` owns Unity input filtering, temporary project generation and the Editor process. Its `editor/` directory contains the C# request protocol and export components. `core/conversion/unity-artifacts.mjs` checks the outputs, creates optional Blender previews and publishes them next to direct exports. Prefabs and their individual renderers have separate files under `Models/<guid>/`. Each file records its role, source file ID when available and converter version.

`core/packages/unreal/` separates source selection, package summary parsing, Pak and IoStore signature checks, inspection and export orchestration. The Unreal CLI operates on this package layer. The native adapter in `core/engines/unreal/bridge/` separates staging, editor selection, project generation, process control and response validation. Its `editor/` packages the trusted Python entry point, dependency resolver, exporters and material reader. `core/conversion/unreal-artifacts.mjs` validates the reported outputs and uses the same artifact store as Unity. The CLI publishes to a managed import directory and scans it with `AssetIndex`. Integration with the durable package queue and conversion cache is pending.

`core/engines/blender/batch.mjs` runs the bundled Python adapter for formats that need conversion. The adapter stages OBJ and glTF dependencies, imports each model once and uses the same scene for the requested derivatives. Legacy previews and package conversions share a serial Blender runner within the server process. The two features have separate scripts and timeout policies.

The CLI and stdio MCP interfaces call `AssetIndex` directly. The MCP connector opens the database read-only and applies a library scope to every asset query.

The Electron main process launches the loopback server in a UtilityProcess and injects an ephemeral authorization header in its dedicated browser session. The isolated renderer can choose a folder or resolve the path of a file selected or dropped in the importer. The desktop app prefers port 8178, permits a configured port, and can fall back to an ephemeral port. Indexed user metadata stays independent of the browser port.
